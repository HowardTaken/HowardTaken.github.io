Photonics and the measurement bench

At UCLA I've moved toward photonics and semiconductor devices. As a SURP Research Fellow in the Terahertz and Infrared Photonics Group, I work with terahertz quantum cascade lasers. They are among the few compact, solid-state sources in a part of the spectrum that is otherwise hard to reach. My main project was a device that had never been measured: a metal–metal waveguide THz QCL. I brought it up, characterized it across bias and temperature, and established its operating envelope: a 2.45–2.61 THz tuning range and a maximum operating temperature of 133 K.

Most of the engineering effort went into the software around the bench. The lab's test setup had been configured by hand through LabVIEW, which made measurements slow and hard to reproduce exactly. I replaced it with a MATLAB automation suite built on modular instrument drivers for the source meter, lock-in amplifier, FTIR spectrometer, and pulse generator. Each driver talks over SCPI, serial, or TCP, and each has a mock version so the whole system can be tested without hardware attached. On top of that sit analysis scripts that extract key device parameters, and a GUI that lets other lab members run standardized tests without editing code. The GUI is deployed to the shared lab PC through a self-updating Git distribution, so everyone always runs the latest version.

That combination is what I enjoy most: a physical device on the bench and the software that makes sense of it. A measurement is only as trustworthy as the pipeline behind it, and I prefer to own both the hardware and the software.

Bringing up a terahertz quantum cascade laser, and automating the bench that measures it

I independently characterized a previously untested metal–metal waveguide THz quantum cascade laser. Along the way, I replaced the lab's manual LabVIEW test configuration with an automated MATLAB measurement and analysis system built on modular instrument drivers.

Background

The terahertz band sits between microwaves and the infrared. It is useful for spectroscopy, imaging, and sensing, but it has historically been hard to generate with compact sources. Quantum cascade lasers (QCLs) are one of the few solid-state options. Unlike a conventional diode laser, a QCL emits light as electrons cascade through a carefully engineered stack of quantum wells, so the emission frequency is set by the layer design rather than by the material's bandgap.

The device I worked on uses a metal–metal waveguide, in which the active region is sandwiched between two metal layers. This geometry confines the optical mode tightly, which helps the laser keep working at higher temperatures. The tradeoff is that light couples out of the device less efficiently, so measurements are sensitive and benefit from careful, repeatable technique.

The problem

The lab's characterization workflow relied on configuring instruments manually through LabVIEW. Every change in operating condition, such as a new bias point, a switch between pulsed and continuous-wave drive, or a new temperature, meant reconfiguring the setup by hand. That made full characterization slow, made it hard to repeat a measurement exactly, and created opportunities for human error between runs.

What I built

I built a MATLAB test automation suite that controls and sequences the whole multi-instrument setup over GPIB from a single program:

  1. Configure
    Lab members set test parameters in a GUI, with no code edits required.
  2. Control
    Modular drivers command each instrument over SCPI, serial, or TCP.
  3. Bias the DUT
    The laser is swept across bias in pulsed and continuous-wave modes.
  4. Acquire
    Optical output and spectra are captured automatically at each operating point.
  5. Analyze
    Scripts generate performance plots and extract device parameters.

The automated characterization pipeline, from test configuration to extracted parameters.

Modular instrument drivers

The core of the system is a set of modular instrument drivers, one per instrument, each built on an interchangeable transport layer (SCPI over GPIB, serial, or TCP):

Source meter

8114A

Every driver has a matching mock instrument that behaves like the real one. That means the full GUI and every test sequence can be validated on a laptop with no hardware attached, so bugs get caught before they cost bench time on a cryogenically cooled device.

  • Characterization sequences. Full test runs bias the device under test and capture its output across pulsed and continuous-wave operating conditions with no manual reconfiguration between steps, which makes results directly repeatable.
  • Data analysis. Analysis scripts process the acquired data, generate performance plots, and extract the parameters that define the device's behavior, so they can be compared with expected operating behavior.
  • GUI and deployment. A MATLAB GUI lets other lab members configure parameters and run standardized validation sequences without touching the underlying code. It is deployed to the shared lab PC through a self-updating Git distribution, so the bench always runs the latest version and every change stays documented.

Parameters extracted

Threshold current density
The current density at which the device begins to lase. It is the main figure of merit for how efficiently the active region reaches optical gain.
Slope efficiency
How much additional optical power the laser produces per unit of additional drive current above threshold.
Characteristic temperature
How quickly the threshold rises as the device heats up. It summarizes the laser's temperature sensitivity and ultimately limits its maximum operating temperature.

Results

Using this system, I brought up the previously untested device and established its full operating envelope. The laser tunes from 2.45 to 2.61 THz with bias and operates up to a maximum temperature of 133 K. The automation suite and GUI remain in use, giving the group a standardized, repeatable way to characterize future devices.

Quantum RAG Assistant

An agentic retrieval-augmented assistant over terahertz photonics papers that checks its own answers for grounding and cites the exact source PDF page. It started as a tool for my own lab reading and grew into a production-style web application.

Stack
Python, LangGraph, ChromaDB, FastAPI, React/TypeScript (Vite), SQLite
Focus
Grounded, cited answers; agentic retrieval; production hardening
Source
github.com/HowardTaken/quantum-rag-assistant

Motivation

My lab research draws on dense THz photonics literature, and finding the right passage across many papers is slow. Keyword search works poorly because the same idea is often described in different terms. I wanted a tool that answers specific questions using the papers themselves and shows exactly where each answer came from.

How the agent works

  • Ingestion. Papers are parsed, chunked, embedded, and stored in a ChromaDB vector database with their page metadata, enabling semantic search by meaning rather than exact wording.
  • ReAct agent. The assistant is a LangGraph ReAct agent that reasons about the question and decides when and what to retrieve.
  • Grader node. Before answering, a grader node checks whether the draft is actually supported by the retrieved passages. If it isn't grounded, the agent reformulates the query and retrieves again rather than answering from weak evidence.
  • Page-level citations. Every answer is cited to the source PDF and page number, so any claim can be checked against the original paper in seconds.

Productionizing it

Once the core agent proved useful, I turned it into a full application:

  • A FastAPI backend and a React/Vite TypeScript frontend.
  • API-key authentication, per-IP rate limiting, and CORS configuration to protect the service and the LLM budget behind it.
  • Per-thread SQLite checkpointer memory, so each conversation keeps its own multi-turn state and follow-up questions build on earlier context.
  • Continuous integration that runs backend and frontend tests and deploys the frontend.

Takeaway

Retrieval quality and the grading loop decide whether answers can be trusted, and the infrastructure (auth, rate limits, persistent state, CI) decides whether anyone else can actually use it. Building both taught me how to take a working prototype to a deployable service.

What the agent does

Given a ticker, the agent works through the same steps an analyst would, calling tools for each one:

  • Fundamentals from the Financial Modeling Prep API.
  • Discounted cash flow (DCF) valuation where it applies.
  • 10-K risk factors and earnings call commentary.
  • Peer comparables to put the numbers in context.

It then writes a Buy/Hold/Sell memo validated against a schema, so every report has the same structure and malformed output is caught instead of shown to the user.

Domain guardrails

A DCF is not meaningful for every company. For banks and insurers, debt, deposits, and float are part of normal operations rather than financing, so free cash flow doesn't capture how the business creates value. The agent detects these companies and reroutes them to a price-to-book plus return-on-equity (P/B + ROE) valuation, the standard approach for financial institutions, instead of producing a confidently wrong DCF.

Shipping it

  • A FastAPI backend and React/TypeScript frontend.
  • Live Server-Sent Events (SSE) streaming of the agent's tool calls, so users watch the research happen step by step instead of waiting on a spinner.
  • A 149-test suite (120 Python, 29 frontend) covering the pipeline, guardrails, and UI.

Each analysis completes in 1–3 minutes, compared with hours of manual research.

Project · 2026

Autonomous Line-Following Robot

An Arduino robot that fuses an 8-sensor IR array into a single tracking error and steers with a tuned PID loop. It recovers when it loses the track and stops at the finish line.

Stack
C++, Arduino, 8-sensor IR array, dual motor drivers
Focus
Sensor fusion, real-time feedback control, robustness
Source
github.com/HowardTaken/ece3-pid-line-follower

Sensing

  • Per-sensor calibration. No two IR sensors respond identically, so each of the eight is calibrated individually and its readings are normalized before use.
  • Weighted-error fusion. The normalized readings are combined with position weights into a single error value representing where the line sits relative to the center of the robot.

Control

A PID controller converts that error into differential speed commands for the dual motor drivers:

  • Proportional action steers back toward the line in proportion to how far off it is.
  • Integral action removes persistent offset, so the robot doesn't settle slightly to one side.
  • Derivative action damps the response, so the robot doesn't overshoot and oscillate.

I tuned the gains to minimize tracking error and oscillation across variable-contrast surfaces, where changes in line and background contrast can push a loop tuned on one surface into oscillation on another.

Robustness

  • Track-loss recovery. If every sensor loses the line, the robot uses its last known error to steer back toward it instead of driving off course.
  • Finish-line detection. The robot recognizes the finish marker and stops on its own.

BMS step-down subsystem

I'm responsible for the part of the battery management system (BMS) board that converts the 14.4 V battery rail into a regulated 9 V rail. The current revision uses a low-dropout linear regulator (LDO). LDOs are simple and quiet, but they regulate by dropping the excess voltage across themselves as heat. Going from 14.4 V to 9 V, a linear regulator can be at most about 9 / 14.4 ≈ 62% efficient, and the rest of the power heats up a sealed underwater enclosure.

I'm developing a buck converter to replace it. A switching regulator stores and releases energy through an inductor instead of burning it off, which improves both conversion efficiency and thermal performance. That means more runtime from the same battery and less heat to manage inside the hull.

Chassis and thrusters

I also contribute to the AUV's chassis frame architecture and thruster configuration with the mechanical team. That work weighs several competing goals:

  • Rigidity. The frame has to stay stiff enough to keep thrusters and sensors aligned without adding unnecessary mass.
  • Buoyancy distribution. How buoyancy and weight are distributed affects the vehicle's resting attitude and how much work the thrusters must do to hold position.
  • Hydrodynamic stability. Thruster placement and orientation determine how predictably the vehicle can be controlled in each direction of motion.

Working on both the electrical and mechanical sides means I handle component integration from both directions, making sure the electronics, wiring, and enclosures fit the frame without compromising it.

Research · UC Santa Barbara · June – July 2024

Bio-inspired snake-scale surfaces for friction reduction

As a student researcher, I engineered prototypes inspired by snake scales to reduce tribological friction, and used quantitative motion analysis to guide each design iteration.

Role
Student Researcher
Tools
CAD, 3D printing, MATLAB, motion-tracking software
Focus
Design for manufacturability, quantitative testing

Snake scales are a well-known example of a natural surface that controls friction through geometry. The project aimed to reproduce that effect in engineered, interlocking scale prototypes.

  • Iterating on manufacturability. Early designs ran into critical 3D-printing tolerance failures, where interlocking features came out too tight or too loose to work as intended. I redesigned the interlocking mechanisms iteratively until the parts printed and assembled reliably.
  • Measuring instead of guessing. I evaluated each prototype with motion-tracking software and processed the resulting displacement and velocity datasets in MATLAB. Comparing designs quantitatively shortened each design iteration cycle.
